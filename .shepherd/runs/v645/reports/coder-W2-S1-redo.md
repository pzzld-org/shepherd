## Prior report's false claim — not repeated

`coder-W2-S1.md` ("Second structural decision" section) asserted: *"Under bare `default`, `build()` still compiles and returns a working `Environment` — it simply keeps minijinja's builtin `tojson` (HTML-escaped, unsorted). This is a documented, intentional degradation of the minimal build."* The audit proved this false: under every feature leg this crate's `Cargo.toml` could produce (bare `default`, `json`, `full`), `minijinja::Environment::new()` had **zero** `tojson` filter, builtin or otherwise, because minijinja's own `json` feature (which gates the `tojson` filter *body*, not just its registration slot) was never turned on anywhere in the dependency graph. I did not repeat this claim; see below for what is now actually true after the fix, which is *not* the same as what the prior report said.

## Resolution chosen: (A) — add `minijinja/json`

Chose **(A)**: added `minijinja/json` to `crates/render/Cargo.toml`'s `json` feature list (file-scope-permitted: feature list only, no dependency/lint/metadata line touched).

**Why (A) over (B):** (A) is closer to the plan's stated intent — Action 4 wants a *real byte divergence* ("a parity test that cannot fail is not a parity test"), and the negative-control test as designed already compares rendered bytes, not error variants. (A) restores exactly the missing piece (the builtin filter body) so that comparison becomes meaningful again, with zero test-logic rewrite and zero new dependency (minijinja's own optional `serde_json` was already resolvable in the lock file). (B) would have required rewriting the test's assertion shape (`assert_ne!` on rendered strings → `assert!` on an `Err(UnknownFilter)`) and would have made the crate permanently unable to prove byte-level parity against Jinja2's builtin at all — a strictly weaker test for a problem (A) fixes for free.

**Verified against minijinja's own source before writing anything** (not assumed): `~/.cargo/registry/src/.../minijinja-2.24.0/src/defaults.rs:129-132` gates the `tojson` builtin registration on `#[cfg(feature = "json")]`, nested inside a block already gated on `#[cfg(feature = "builtins")]` (which this crate has always had on). `minijinja/Cargo.toml`: `json = ["serde_json"]`. Confirmed the fix is exactly minimal: one feature-list line.

## Second consequence resolved: the doc claim is now made TRUE, not just "less false"

Adding `minijinja/json` to shepherd-render's **own optional `json` feature** (not to `default`/`std`) means the builtin and the override are now coupled 1:1 — they turn on and off together, always. That makes the *original* doc sentence ("without \[json feature\], env keeps the builtin") structurally impossible to ever be true as originally worded (there is no state where the override is off but the builtin is on), so I did not merely patch the wording — I rewrote the comment block in `env.rs` to state what is actually true post-fix:

- Under `json`/`full`: `sorted_tojson` is registered and minijinja's builtin body now compiles in too (so the negative control has a real builtin to diverge against — confirmed by the passing test below).
- Under bare `default` (no `json` feature): **both** compile out together. `minijinja/json` lives inside this crate's own optional `json` feature, not `default`/`std`, so the returned `Environment` still has **no** `tojson` filter at all in the minimal build. A template using `| tojson` (`boot-prompt.md.j2`'s `peer_teammate_names`, `seed.md.j2`'s `sprint_dependencies`/`parallel_with`) hard-fails with `ErrorKind::UnknownFilter` in the minimal build — there is no HTML-escaped/unsorted fallback, because there is no fallback at all. This is unchanged behavior from before the fix (resolution (A) only restores the builtin on the feature leg where the override is *also* on, which is exactly the leg the negative-control test runs under) and remains a real, intentional gap for this step's scope: no default-feature caller renders a `tojson` template today (`shepherd-sdk`'s own `json` feature already forwards to `shepherd-render?/json`), but any future default-feature caller of such a template (`crates/cli`, W2-S3+) must enable this crate's `json` feature or accept the hard render error. This is now documented accurately in `env.rs`, not glossed over.

## FINDING 2 answer (MEDIUM, non-blocking — not fixed, per instructions; answering only)

**Is a shared shape extractable later?** Yes, structurally — the recursive tree-walker (`write_value`/`write_array`/`write_object`/`write_json_string`) is the same shape in both `crates/core/src/run/canonical.rs` and `crates/render/src/filters.rs`; only the formatting constants differ (indent width vs. none, `ensure_ascii` true vs. false, separator strings). A single generic writer parameterized by a small `JsonStyle { indent: Option<usize>, item_sep: &str, kv_sep: &str, ensure_ascii: bool }`-shaped struct (or equivalent) could serve both call sites with zero behavior change to either caller.

**What would have to change in `crates/core` to allow it:**
1. `to_canonical_string`'s backing writer functions would need to be **parameterized** by style instead of hardcoding `models_run.py`'s 2-space-indent/`ensure_ascii=True` constants inline — currently they're not a reusable primitive, they're a fixed-format function.
2. The resulting parameterized writer would need its visibility **widened from `pub(crate)`** so `crates/render` (a different crate) can call it — a public-API surface change to `shepherd-core`.
3. Given `crates/core/**` is `must_not_touch` for **both** W2-S1 and W2-S2 (by design — this sprint's steps are scoped not to touch the engine crate), neither step's `[FILE-SCOPE]` permits doing this today. It's a clean candidate for a follow-up issue against whichever future step next touches `crates/core`, as the auditor already recommended (no GH issue filed by the auditor; not filing one from this redo either, since git write and issue creation are outside this role's write boundary and the redo brief did not ask for one — flagging here so the conductor can decide whether to open it).

I did not attempt this in the redo: it is explicitly non-blocking per the dispatch, and doing it would require touching `crates/core/**`, which remains `must_not_touch`.
