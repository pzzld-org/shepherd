## Findings

### 1. Codex CLI plugin surface, as it ships today

**Manifest.** The only required file is `.codex-plugin/plugin.json`, minimal fields `name`, `version`, `description`. "Only `plugin.json` belongs in `.codex-plugin/`. Keep `skills/`, `hooks/`, `assets/`, `.mcp.json`, and `.app.json` at the plugin root." (`developers.openai.com/codex/plugins/build`) — this is the **complete enumerated set** of optional plugin components: `skills/`, `hooks/` (default `hooks/hooks.json`, overridable via a `hooks` entry in `plugin.json`), `.mcp.json`, `.app.json`, `assets/`. **No `prompts/`, `commands/`, or `agents/` entry exists in this schema.** A Codex plugin cannot bundle a command/prompt file or a role-definition file — matches D1's local finding (installed `codex-shepherd@1.0.2` bundle contract), now confirmed against the official manifest spec rather than one installed instance.

**Hooks.** Event taxonomy (`developers.openai.com/codex/hooks`): during a turn — `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStop`, `Stop`; session lifecycle — `SessionStart`, `SubagentStart`, `SessionEnd`. Three-level schema (event → matcher group → command handler). Trust gate: "Before a non-managed command hook can run, Codex requires you to review and trust the exact hook definition," bypass via `--dangerously-bypass-hook-trust`. Handler env vars: `PLUGIN_ROOT`, `PLUGIN_DATA`, plus **Claude-compatible aliases `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`** — Codex deliberately shims Claude's own env-var names for hook-script portability. Current default: "Hooks are enabled by default. Disabling requires: `[features] hooks = false`" — consistent with D1's live local read (`hooks = stable, true`).

Historical note (not a live conflict, a version-time evolution, SECONDARY source `agenticcontrolplane.com`): hooks were opt-in pre-v0.124.0 via `[features].codex_hooks = true`; became stable/on-by-default at v0.124.0 (2026-04-23). The locally-installed `codex-cli 0.147.0` (per D1) is well past that line, so "on by default" is the operative fact for the compiler.

**Command/prompt surface — refines D1's residual 1.** D1 closed residual 1 as "there is no Codex slash-command surface at all... Codex has nowhere to put one," reasoned from the plugin bundle contract and one box's absent `~/.codex/prompts`. That conclusion holds for **plugins** (confirmed above: the manifest schema has no prompts/commands slot). But Codex CLI itself, **independent of the plugin system**, does ship a native (now-deprecated) custom-prompts mechanism: `~/.codex/prompts/*.md`, "Codex scans only the top-level Markdown files in that folder," YAML frontmatter `description:` ("Shown under the command name in the popup") and `argument-hint:` ("Document expected parameters"), invoked via `/prompts:<name>` from the slash menu. Explicit deprecation notice, verbatim: **"Custom prompts are deprecated. Use skills for reusable instructions that Codex can invoke explicitly or implicitly."** It "lives in your local Codex home directory... not shared through your repository" — user-local, not repo/plugin-distributable, and OpenAI is actively steering users off it. (`developers.openai.com/codex/custom-prompts`)

**Compiler consequence, sharpened:** the content compiler must emit **zero** Codex command surface — not merely because plugins can't bundle one (D1's finding), but because the one native mechanism that *could* carry a command file is (a) not plugin-bundlable and (b) officially deprecated in favor of skills. Any temptation to shim `content/commands/*.md` into a per-user `~/.codex/prompts/` drop is a dead end twice over.

### 2. Pi CLI — tool allowlist, config, agent-definition, hook/lifecycle surface

**`--tools`/`-t` (source, not docs-site prose): "Comma-separated allowlist of tool names to enable / Applies to built-in, extension, and custom tools."** `--exclude-tools`/`-xt`: "Comma-separated denylist of tool names to disable / Applies to built-in, extension, and custom tools." `--model`: "Model pattern or ID (supports \"provider/id\" and optional \":<thinking>\")." No subagent, parallel, or team flag exists anywhere in `args.ts`. (`github.com/badlogic/pi-mono/.../cli/args.ts`) — confirms D1's local probe (`--tools` is a strict-replacing allowlist) against the upstream source rather than the bundled binary's `--help` text.

**Config precedence — confirmed 2-tier, matches D1.** "Pi uses JSON settings files with project settings overriding global settings." Tiers: `~/.pi/agent/settings.json` (global) < `.pi/settings.json` (project). "Nested objects are merged," not replaced wholesale — e.g. project `compaction.reserveTokens` overrides while global `compaction.enabled` persists. Configurable surface spans model/thinking defaults, UI, shell, `defaultTools`, `sessionDir`, and resource paths (`extensions`, `skills`, `prompts`, `themes`); `defaultProjectTrust` (`ask`/`always`/`never`) gates whether project extensions execute at all. (`github.com/badlogic/pi-mono/.../docs/settings.md`)

**Agent-definition format: absent natively, present only as a third-party clone.** Pi ships no declarative role/agent file. The only Markdown+YAML-frontmatter agent format in the ecosystem comes from the third-party `@tintinweb/pi-subagents` extension: `model` ("`provider/modelId` or fuzzy name, e.g. `\"haiku\"`, `\"sonnet\"`" — fuzzy resolution tolerates `.`/`-` as equivalent and an optional trailing date stamp), `tools`, `description`, `thinking` (off/minimal/low/medium/high/xhigh/max), `max_turns`, `allowed_subagents`, `isolated`. This is an explicit, self-described clone of Claude's convention, not a Pi-native concept — the README calls it "Claude Code Look & Feel." (`github.com/tintinweb/pi-subagents`)

**Hook/lifecycle surface: an extension event bus, not a hooks.json.** Full lifecycle catalog from source (`raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/docs/extensions.md`): startup (`project_trust`, `session_start`, `resources_discover`); user input (`input`, `before_agent_start`); agent execution (`agent_start`, `turn_start`, `context`, `before_provider_headers`, `before_provider_request`, `after_provider_response`); tool execution (`tool_execution_start`, `tool_call`, `tool_execution_update`, `tool_result`, `tool_execution_end`); messages (`message_start`, `message_update`, `message_end`); model/thinking (`model_select`, `thinking_level_select`); session management (`session_info_changed`, `session_before_switch`, `session_before_fork`, `session_before_compact`, `session_compact`, `session_before_tree`, `session_tree`, `session_shutdown`); `user_bash`. Tool-call interception: **"Fired after `tool_execution_start`, before the tool executes. Can block."** — `event.input` is mutable in place; guard example verbatim: `if (event.input.command.includes("rm -rf")) { return { block: true, reason: "Dangerous command", terminate: true }; }`. This matches D1's locally-probed contract exactly, now grounded in the upstream doc rather than the bundled copy. Extensions can shell out (`pi.exec(command, args, options?)`) but the doc is explicit that no team primitive exists at this layer, and imposes lifecycle discipline: "Do not start background resources such as processes, sockets, file watchers, or timers from the factory. Defer background resource startup until `session_start`... Register an idempotent `session_shutdown` handler."

### 3. Subagent spawn, model pinning, parallel fan-out — per harness

**Claude Code.** Spawn via the `Agent` tool (renamed from `Task` in v2.1.63; old references still work as aliases), `@`-mention, or `--agent <name>` to run the whole session as that agent. **Model resolution is a 4-tier explicit chain**, verbatim: "1. The `CLAUDE_CODE_SUBAGENT_MODEL` environment variable... 2. The per-invocation `model` parameter 3. The subagent definition's `model` frontmatter 4. The main conversation's model." (`code.claude.com/docs/en/sub-agents`) Parallel fan-out is native at two layers: (a) subagents "run in the background by default" as of v2.1.198, and the docs' own example pattern is "Research the authentication, database, and API modules in parallel using separate subagents"; (b) Agent Teams spawn N teammates that "work independently, each in its own context window" and communicate directly — "Spawn three teammates to explore this from different angles" is a documented first example. (`code.claude.com/docs/en/agent-teams`)

**Codex.** Spawn via the MultiAgent tool family — `spawn_agent`, `send_message`/`send_input`, `followup_task`, `wait_agent`, `list_agents`, `close_agent` — feature-gated by `features.multi_agent`: **"Enable multi-agent collaboration tools (`spawn_agent`, `send_input`, `resume_agent`, `wait_agent`, and `close_agent`) (stable; on by default)."** (`learn.chatgpt.com/docs/config-file/config-reference`) Parallel fan-out is config-capped by `agents.max_concurrent_threads_per_session` (current key; `agents.max_threads` is a documented "Legacy alias"). D1's locally-read `shepherd.codex.toml` pins its own tighter `max_concurrent_children = 3`, which is the sibling port's app-level choice, not the harness default. A secondary, unofficial source claims the native default is 6 concurrent threads with `max_depth = 1` (child can spawn, no deeper recursion) — the fetched official reference excerpt names the keys but not a bare numeric default, so **treat "6" and "depth 1" as UNVERIFIED against primary docs**, plausible but not confirmed here.

**Model pin on Codex — a live, unresolved conflict between documented schema and shipped default runtime.** The config reference documents per-spawn override support: `agents.default_subagent_model` — "Default model for spawned agents. **An explicit spawn model takes precedence.**" — and a matching `agents.default_subagent_reasoning_effort`. This implies `spawn_agent` accepts `model`/`reasoning_effort` as ordinary arguments. But `github.com/openai/codex/issues/20077` (opened 2026-04-28, **still open**, no maintainer fix) reports the opposite for the shipped default: `spawn_agent` defaults `fork_turns` to `"all"` (full-history fork) when omitted, and full-history mode **rejects** role/model/reasoning overrides outright, verbatim rejection message: **"Full-history forked agents inherit the parent agent type, model, and reasoning effort; omit `agent_type`, `model`, and `reasoning_effort`, or spawn without a full-history fork."** A separate community thread (`community.openai.com/.../restoring-subagent-roles-model-and-reasoning-in-multi-agent-v2/1386513`, 2026-07-11) documents the practical workaround users have converged on: encode the role in `task_name`, inject the real role/model metadata through a `PreToolUse` hook instead of the `spawn_agent` call, and keep `hide_spawn_agent_metadata = true`. **Net verdict: model pinning on Codex is EMULATABLE, not cleanly AVAILABLE** — it is reachable only by explicitly requesting a non-full-history spawn (`fork_turns: "none"`) or by routing the pin through a hook-injected side channel, not by calling `spawn_agent` the documented way. This directly threatens the sibling port's `shepherd.codex.toml [profiles]` `reasoning_effort` mechanism (D1 §Engineer follow-up) — that config may silently not apply against the default full-history-fork spawn path, and D1 did not test this because it read config, not runtime behavior.

**Pi.** No native spawn primitive at all — confirmed by the complete `extensions.md` event catalog above containing no spawn/team/parallel-agent event, and by `args.ts` containing no subagent flag. The only implementation is the third-party `@tintinweb/pi-subagents` extension (install: `pi install npm:@tintinweb/pi-subagents` or `pi -e ./src/index.ts`), which provides "**Parallel Background Agents**: Spawn multiple agents that run concurrently with automatic queuing (configurable concurrency limit, default 4) and smart group join," per-agent `model:` in its own frontmatter dialect, and "mid-run steering, resume completed sessions." Schedule state persists at `<cwd>/.pi/subagent-schedules/<sessionId>.json` with PID-based file locking. The README states plainly: **"The project is currently in early release status"** — this is unvetted third-party software, not a harness guarantee, exactly as D1 already flagged as Hazard 2.

## Refinements to D1 (do not re-litigate, only what changed)
