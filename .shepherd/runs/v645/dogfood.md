| DF-11 | HIGH | **Every sub-flock completion leaks into ROOT's context, and it is expensive.** The self-contained `@engineer`'s own sub-agents (`D1 harness surface probe` @discovery, `A1 Rust landed-state` @auditor) both fired full `<task-notification>` payloads into root's stream — ~4-5k tokens each, for work root did not dispatch and must not materialize. `agents/shepherd.md §Coordinate RELAY` (#224) prescribes relaying VERBATIM to the owning lead on the same wake, which on a 5+ agent intro wave means root pays the full payload cost twice: once to receive, once to relay. The doctrine was written to stop payloads being LOST; on this substrate they are DUPLICATED instead, and the prescribed remedy multiplies the waste. Root relayed D1 verbatim (~4k), then switched to compact relay + an explicit "are you getting your own results?" query. The self-contained-engineer topology exists precisely to keep root lean, and this defeats it.<br><br>**Mechanism, identified after n=2:** these are Dynamic Workflow `agent()` completions, not misrouted in-context `Agent()` calls. `Workflow` runs in the background and ends the dispatching lead's turn, so the lead reads `idle` in `shctx teammate liveness` for the whole workflow duration while its `agent()` children complete — and each child's `<task-notification>` goes to the **task-tree owner** (root), not to the lead that authored the call. The lead does get its results, in the script's return array, when the script finishes. So the #224 diagnosis ("misrouted from a teammate-conductor's in-context `Agent()` fan-out") is the wrong mechanism for the workflow path, and the prescribed cure (relay verbatim, same wake) is actively wrong here: it duplicates a payload the lead already has coming. **Two separate fixes fall out:** (1) `§Coordinate RELAY` must branch on vehicle — verbatim relay stays correct for in-context `Agent()` leaks, but workflow-child notifications are informational and root must NOT relay them; (2) root's stall detector must not read a workflow-driving lead's `idle` as a stall — `TEAMMATE-STALL` would fire on a perfectly healthy lead at the 5-min heartbeat threshold, and only the `declared_state: in-progress` override (migration 0019) accidentally prevents it here. | n=2 in one wave; D1 122,024 subagent tokens / A1 146,393; both surfaced in full to root; lead `idle` 867s with `verdict ok` only because declared in-progress | FIX-THIS-RUN |

Every stall guard keyed on it (`TEAMMATE-STALL`, the 5-min staleness alert, `presumed-crashed`, `shctx teammate prune --crashed`) is reading a number that has no relationship to teammate health. **Compounding defect: the two hooks key differently.** `teammate_idle.sh` matches by NAME (and did fire — `status` is `idle`), `teammate_heartbeat.sh` matches by SESSION_ID (and cannot fire). | DF-13 | CRITICAL | **`status='idle'` is a one-way latch, and it traps root's drive loop permanently.** `coordinate_drive_guard.sh` blocks root from ending a turn while `IDLE_Q` returns non-zero: `WHERE (declared_state <> 'complete' AND (declared_state IN ('in-progress','error','idle') OR ms_since_seen <= 300000)) AND (status='idle' OR declared_state='idle')`. `teammate_idle.sh` sets `status='idle'` (matching by NAME — it works). The ONLY thing that clears it is `teammate_heartbeat.sh`'s `CASE WHEN status='booting' THEN 'active'` — which (a) never fires at all per DF-12's session_id mismatch, and (b) **only transitions `booting`, never `idle`**, so it could not clear the latch even if it did fire. Root tested every available verb: `shctx teammate heartbeat` advanced `last_seen_at` from 1201s to 0 and left `status='idle'` untouched; `shctx teammate state --set` writes `declared_state`, not `status`; there is no `status --set` verb. Guard predicate re-evaluated after the heartbeat: still `LIVE=1, IDLE=1`. **Once any teammate goes idle even once, root can never cleanly end a turn for the rest of the run**, regardless of how completely it drains — the state the guard demands root clear is unclearable by any action root can take. The guard's own comment asserts "the ONLY root-clearable state this guard keys on is an IDLE teammate whose payload root must materialize," and that assertion is false.<br><br>**Root cause is a semantic collision, not a missing verb.** The coordinate loop is built on `idle` meaning *"finished its wave, payload awaiting materialization"* — root materializes, prunes, and the count drops. On this substrate `TeammateIdle` fires whenever a teammate **ends a turn**, and a lead that dispatches a Dynamic Workflow ends its turn immediately (the workflow runs in the background — see DF-11). So the doctrine's own mandated fan-out vehicle puts every lead into `idle` for the entire duration of its productive work, and the only prescribed remedy (prune it) would kill a teammate mid-wave. The two meanings need separate states, or the guard must key on `declared_state` alone. | root ran the full verb sweep against a live teammate; before/after rows and predicate counts recorded above | FIX-THIS-RUN |
